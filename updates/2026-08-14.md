# 2026-08-14 — First deployment

Deployed Scion `main` @ `90bf246e` onto a pre-existing, internal-only GCE VM (Ubuntu 24.04)
in a shared VPC: no external IP, IAP-only SSH, corporate package mirrors, DNS managed by a
network team, and a service account with narrow scopes.

**Outcome: working hub**, but not via the documented path.

## The starter-hub scripts didn't fit

`gce-demo-deploy.sh` runs six steps. Four didn't apply to us:

| Step | Why not |
|---|---|
| Preflight | Checks for things we don't have and can't get |
| Provision | The VM already existed |
| Telemetry SA | Blocked by org policy on SA keys |
| DNS + certs | `gce-certs.sh` needs a Cloud DNS zone and `dns.admin`; we have neither, and with no public IP Let's Encrypt is impossible either way |

We reimplemented the applicable stages by hand, which is how most of the findings below
surfaced.

## What went wrong, and what it taught us

**The web build failed with a misleading error.** `npm install` reported:

```
npm error Exit handler never called!
```

which names npm as the culprit. The real cause was only visible in
`~/.npm/_logs/*-debug-0.log`: ~15 concurrent `.tgz` fetches all failing `ECONNRESET` against
`registry.npmjs.org`. Metadata requests succeeded and ~197 packages installed first, so it
looked like a flaky partial install rather than a network policy block. Fixed by pointing npm
at our internal mirror. → **finding 9**

**The Go version pinned in the scripts is stale.** Scripts install Go 1.23.0; `go.mod`
requires 1.26.1. → **finding 1** *(severity later corrected — see 2026-08-18)*

**`gce-start-hub.sh` starts by pushing to the upstream repo.** Step 1 is
`git push origin main`, which fails for anyone who isn't a maintainer of the Scion repo, at
the very start of a deployment. → **finding 2**

**A config key in the settings template does nothing.** `default_runtime` is written into
`settings.yaml` but doesn't exist in the Go config schema; the hub silently strips it on
startup. → **finding 3**

## Getting OIDC working

Configured Keycloak SSO as a public client. Two problems with the setup guide:

- The documented redirect URI route **does not exist**. The real one is
  `{BaseURL}/auth/callback/{provider}`. → **finding 4**
- The guide lists HTTPS as a prerequisite. It isn't — the hub derives its session cookie's
  `Secure` flag from the base URL scheme, and we ran OIDC login successfully over plain HTTP.
  This mattered: on an internal host, obtaining a certificate can mean a multi-day PKI
  ticket, and we nearly blocked on it before testing. → **finding 5**

Then removed dev-auth. The documented cleanup command targets the wrong username, so it
silently deletes nothing. → **finding 6**

## Also noted

- No supported path for internal-only / bring-your-own-cert / IAP deployments → **finding 7**
- Unknown `settings.yaml` keys vanish with no warning → **finding 8**
- Minor items: no `--version` alias, archived NATS still installed, a placeholder registry in
  `hub.env.sample` that looks real enough to carry into a deployment → **finding 10**
