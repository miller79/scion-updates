# 2026-08-17 — Hardening, TLS, telemetry

Prepared the hub for a wider test group. Audited the exposure surface, moved TLS onto a load
balancer, and tried to get the metrics dashboard working. Upgraded to `1b3c9418` along the
way.

## Security audit before widening access

**The session signing secret was readable by any local user.** The upstream systemd template
passes `--session-secret ${SESSION_SECRET}` on `ExecStart`; systemd expands it, so the value
lands in the process table:

```
$ ps -eo args | grep scion
... --session-secret <the-actual-secret> ...
```

No sudo required, and `hidepid` isn't set on a default Ubuntu image. Since that secret signs
session cookies, anyone with a shell could forge a session for any user, including an admin.

The fix is a one-line deletion — `resolveSessionSecret()` already falls back to the
`SESSION_SECRET` environment variable, which the unit supplies via `EnvironmentFile`. Same
value, no exposure. → **finding 13**

**Secrets are stored in plaintext.** `toStoreSecret()` assigns the raw value into a column
named `encrypted_value`, and a code comment claims writes are rejected without a production
backend — but `ErrNoSecretBackend` is never returned anywhere. An operator reading either the
comment or the column name would reasonably conclude their secrets are protected. → **finding 11**

**File permissions were loose** — database at `644`, settings at `775`. Tightened.

**Worth saying: the secrets *authorization* layer is sound.** We audited it specifically
before letting more people in. No user-facing endpoint returns a secret value, and scoping is
properly enforced. The gap in finding 11 is at-rest storage only.

## TLS

Enabled HTTPS via Caddy's internal CA as an interim, then handed termination to an F5 BIG-IP
VIP holding a real wildcard certificate. Verified the cert chain validates without `-k`.

**One trap found along the way.** Pointing browsers at HTTPS meant agents would be dispatched
to a URL their containers couldn't validate. `hub.env.sample` advertises `SCION_HUB_ENDPOINT`
for exactly this split — but that variable name **binds to nothing**. The env provider
requires a `SCION_SERVER_` prefix. Our first attempt silently did nothing; the dispatcher log
still showed the HTTPS URL. Nothing errored, and it would have failed at first agent launch
with an opaque TLS error. → **finding 12**

## Telemetry

The in-product Metrics dashboard returned:

```
503 metrics_unavailable
"Metrics dashboard is not configured (no telemetry project ID)"
```

Two separate causes, and fixing either alone isn't enough:

- The `settings.yaml` template omits `telemetry.cloud.gcp_project_id`, which is the only key
  the hub reads to build the dashboard service. Confusingly, `hub.env.sample` *does* ship a
  similarly-named variable — but that one feeds the agent-side exporter, not the hub's own
  dashboard. → **finding 14**
- The provision script grants `logging.viewer` but not `monitoring.viewer`, so even once the
  service is constructed it can't read the metrics it just wrote. The asymmetry looks
  accidental. → **finding 15**
