# 2026-08-18 — Authorization findings, and a correction

Upgraded to `1933d359`, ran a multi-user security test, and corrected a claim we got wrong.

## A correction first

We previously described **finding 1** (Go pinned to 1.23.0 against a `go.mod` requiring
1.26.1) as a **hard build failure**. That was wrong, and we'd asserted it without testing —
we had pre-emptively installed the newer toolchain and never actually observed a failure.

Tested properly:

```
default GOTOOLCHAIN (auto):  go: downloading go1.26.1  →  BUILD SUCCEEDED
GOTOOLCHAIN=local:           go.mod requires go >= 1.26.1 (running go 1.23.0)
```

Go's toolchain auto-download quietly papers over the stale pin whenever the network allows
it. The finding is downgraded from Blocking to High, and rewritten with the test output. It's
still worth fixing — the provisioned toolchain isn't the one that builds the binary, and it
*does* fail hard on air-gapped hosts or with `GOTOOLCHAIN=local` — but it is not the
showstopper we called it.

## Multi-user security test

Two users each created a project and an agent. **Each could see the other's project.**

Traced to a policy seeded at first startup (`pkg/hub/seed.go`):

```go
Name:         "hub-member-read-all",
ResourceType: "*",                       // every resource type
Actions:      []string{"read", "list"},
Effect:       "allow",
```

bound to the `hub-members` group — and every user is auto-joined to that group on login. So
**any authenticated user can read every project, agent, and resource on the hub.**

What makes this a defect rather than a preference: the policy engine is **default-deny**, and
projects carry a `visibility` field supporting `private` / `team` / `public`. Both are
overridden by the one wildcard seed. A project created `private` displays as private and is
readable by everyone — the field is currently inert. → **finding 16**

To be precise on severity: the grant is `read` + `list` only. Writes still hit default deny,
and we confirmed a non-owner could not modify another user's project. This is visibility
exposure, not a write hole.

**A related discovery:** the `viewer` role is in the ent enum, selectable from the admin UI,
and the default for federated identities — but it is **never consulted in any authorization
decision**. The only role check anywhere is `Role() == "admin"`. `member` and `viewer` are
functionally identical, so demoting someone to "viewer" expecting read-only does nothing.
→ **finding 17**

## We tested a fix

Rather than leave finding 16 as "narrow it somehow", we ran the change and measured it.

Replaced the wildcard with four type-specific policies — `template`, `harness_config`,
`skill`, `broker` — then deleted `hub-member-read-all`. These must be four separate policies:
`matchesResource` does plain string equality on `ResourceType`, so `"*"` is the only special
value.

Measured A/B, same user and token, only the policy set changed (the user was demoted from
`admin` to `member` for the test, since the admin bypass would otherwise mask the result):

| | wildcard present | wildcard removed |
|---|---|---|
| Projects visible | 3 (incl. another user's) | **1 — own only** |
| Agents visible | 2 | **1 — own only** |
| Templates | 1 | 1 (preserved) |
| Skills | 0 | 0 (preserved) |
| Brokers | 1 | 1 (preserved) |
| Harness configs | 7 | 7 (preserved) |

Every endpoint still returned HTTP 200. Project isolation restored; shared building blocks
intact. A second, genuinely non-admin user confirmed independently that they could no longer
see the other project.

**Not verified:** a member creating an agent end to end. Readable templates and brokers are
necessary but may not be sufficient. Offered as a candidate default, not a proven-complete
one.
