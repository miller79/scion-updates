# 2026-08-19 — Fixing isolation broke membership

Yesterday's fix for finding 16 worked. Today we found what it broke, and it turns out the two
are inseparable.

## The symptom

Added a user to a project as a `member`. They still couldn't see the project.

## The cause

When a project is created, Scion auto-creates a members group and exactly two policies
(`createProjectMembersGroupAndPolicy`):

```
project:<slug>:member-create-agents             agent                 ["create","stop_all"]
project:<slug>:member-assign-service-accounts   gcp_service_account   ["assign"]
```

**Neither grants `read` or `list` on the project itself.** And the `isProjectOwnerOrAdmin`
baseline only fires for group role `owner` or `admin` — not `member`.

Walking the authorization chain for a project member:

| Step | Result |
|---|---|
| Admin bypass | no — they're a member |
| Owner bypass | no — someone else owns it |
| `isProjectOwnerOrAdmin` | **no** — only `owner`/`admin`, not `member` |
| Policy evaluation | the two per-project policies don't cover `project: read` |
| Default | **deny** |

So a project member can create and stop agents in a project **they cannot see**.

This never shows up on a stock install, because the `hub-member-read-all` wildcard grants
read on everything and quietly papers over it. It only appears once you narrow that wildcard
for isolation — which is exactly what finding 16 recommends.

**The two findings are coupled: fixing 16 without fixing 18 hides projects from their own
members.** Recorded as **finding 18**.

## The fix, verified

One project-scoped policy per project, bound to that project's members group:

```
scopeType:    project
scopeId:      <project-id>
resourceType: project
actions:      ["read","list"]
effect:       allow
```

Result as a member: **2 projects visible** — one owned, one joined — and still nothing
unrelated. Templates, brokers and harness configs unaffected. Confirmed to survive a hub
restart, which is now a standing part of how we verify anything here.

One level down is the same shape again: the per-project policies grant `agent: create/stop_all`
but not `agent: read/list`, so a member sees the project and not the agents inside it. Whether
that's wanted is a product decision — but right now it's an accident rather than a choice.

## What this says about the isolation story

Stepping back, the picture for an operator wanting project isolation out of the box:

| Control that looks like it should work | Reality |
|---|---|
| `visibility: private` | inert — overridden by the seeded wildcard |
| `viewer` role | inert — never consulted in any authz decision |
| Project membership | grants agent create/stop, but not read |
| Admin UI toggle | doesn't exist |

There is **no supported way to turn isolation on**. Getting there means knowing that
`hub-member-read-all` exists, that deleting it silently re-seeds, that `matchesResource` is
exact-string equality so you need one policy per type, and that per-project read isn't
auto-created. We only assembled that by reading the source.

To be fair on severity: this is **read visibility, not a write hole**. Non-owners can't modify
or delete another user's project, agent creation is already restricted to project members, and
secret scoping is genuinely enforced. The confidentiality boundary is missing; the integrity
boundary isn't.

And we'd still call it a gap rather than a stance, because the codebase argues for isolation:
default-deny engine, a `visibility` field with three values, per-project member groups with
three roles, and a dedicated `isProjectOwnerOrAdmin` baseline. Someone designed for this. One
seeded wildcard overrides it, and the per-project seed is missing the policy that would make
membership mean something.

Three changes would close it: add `project: read/list` to the per-project seed, make
`visibility` actually enforced, and either implement `viewer` or remove it.

**Findings recorded: 18. Finding 16 amended with the framing above.**
