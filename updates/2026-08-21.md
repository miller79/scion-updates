Every project created after our manual fix got the two auto-created policies
(`agent: create/stop_all`, `gcp_service_account: assign`) and **no read policy**. So isolation

requires a hub admin.

The failure is silent: you add a teammate, nothing happens, no error.

## Fixed with an idempotent backfill

Nine policies across five projects, two per project:

```
project:<slug>:member-read-project   project   [read, list]
project:<slug>:member-read-agent     agent     [read, list]
```

Dry-run first, then applied; a second run was a clean no-op (`created=0 skipped=10 failed=0`),
so it is safe to schedule.

## The read/attach boundary — and getting it wrong first

The requirement: project members should **see** agents in their projects, but must not open a
terminal on someone else's agent.

That boundary already exists in the code — `isReadClassAction` covers only `read` and `list`,
while PTY, exec and message all route through `ActionAttach`. So granting `read`/`list`
without `attach` should do it.

**Our first test appeared to confirm it, and was worthless.** Every call returned 403 —
including against an agent we owned. That last part is what gave it away: the control case
failed, so the test was measuring something else.

The cause: we were testing with a personal access token. A PAT is a `ScopedUserIdentity`, and
`enforceUATConstraints` runs *before* every other check, including the admin bypass — denying
anything outside the token's project or scope list. List endpoints do not apply those
constraints; single-resource GETs do. So the results were both wrong and internally
inconsistent.

Re-tested via the policy engine directly (`POST /api/v1/policies/evaluate`, callable by "admin
or the evaluated principal"), as a genuine `member`:

| Agent | Owner | read | attach | message |
|---|---|---|---|---|
| someone else's | another user | ALLOW *(policy match)* | **DENY** *(default deny)* | **DENY** |
| own | self | ALLOW *(resource owner)* | ALLOW | ALLOW |

Exactly the boundary intended.

One nuance worth recording: project owners/admins **can** attach to any agent in their project
via `isProjectOwnerOrAdmin`. Plain members cannot. We assume that is intended and have flagged
rather than changed it.

## New finding

**19 — no way to import a template except from a URL or server-side files.** Template import
requires `sourceUrl`; the per-project endpoint also accepts a workspace path. There is no
upload route — nothing in the template flow parses `multipart/form-data`.

In an enterprise that is awkward: getting a template in means pushing it to a git remote the
hub can reach, or having shell access to the host. "Here is a zip, please add it" has no
answer.

Two things make it a smaller ask than it sounds: `extractZip()` already exists in
`pkg/config/remote_templates.go` for remote archives, and `multipart/form-data` upload is
already used elsewhere in the hub (`admin_allow_list.go`, `admin_user_invite.go`). So it is
wiring, not new capability.

Filed as a feature request rather than a defect.
