# 2026-08-24 — Secret Manager, and two ways it does not do what you would assume

Our IAM team finished the GCP-side work, so the hub moved off the local secrets backend onto
GCP Secret Manager, and off local disk onto a GCS bucket. Both work. Getting there turned up
four new findings, two of them serious, and one of them is the sort of thing that would have
quietly destroyed a production deployment months later.

## The infrastructure side landed cleanly

All six phases of the runbook we handed over were done: a dedicated service account, a custom
role, project and bucket bindings, Data Access audit logs for Secret Manager, and the VM moved
onto the new identity.

Worth noting because it is easy to get wrong: the custom role was created with exactly the
five Secret Manager permissions the hub actually calls — `secrets.create`, `secrets.get`,
`secrets.delete`, `versions.add`, `versions.access` — and nothing else. No
`roles/secretmanager.admin`, no `setIamPolicy`. The storage grant is scoped to the single
bucket rather than the project. That is the least-privilege line holding under real
operational pressure, which does not always happen.

## Phase 7: both backends live

Two lines of config, one restart:

```
GCS storage configured: gs://<bucket>
Secret backend configured: gcpsm
```

Secrets now land in Secret Manager with matching Data Access audit entries attributed to the
hub's service account. Zero permission errors after the identity swap. The bucket picked up
the bootstrapped template files immediately.

## The hub_id trap — finding 20

The VM restart that attached the new service account also changed the machine's hostname from
its short form to its fully-qualified form. That is ordinary GCE behaviour.

`hub_id` is derived from the hostname when it is not explicitly set. And `hub_id` is the
namespace for secrets:

```
scion-{scope}-{sha256(hubID:scopeID)[:12]}-{name}
```

and for object storage: `hubs/<hub_id>/...`.

So the hostname change silently moved the hub to a completely unrelated secret namespace. We
verified the derivation by hand — hashing the two observed ids reproduced exactly the secret
prefix we could see in Secret Manager, and the two prefixes have nothing in common.

Nothing failed. The hub came up healthy and reported itself fine. Had this happened a few
months into a real deployment, every stored secret would have become unreachable in one
restart, with a healthy-looking hub and no error to explain it.

There is a warning, but it only appears when a storage bucket is configured, it is one line
among several hundred at startup, and it describes the risk as being about "multi-hub
deployments" — not "your secrets are about to be orphaned". We only saw it because we were
reading the log for an unrelated reason.

Pinned `hub_id` and `hub_name` explicitly; the warning is gone and the namespace is stable by
configuration rather than by luck.

## Secret Manager does not remove the plaintext — finding 21

This one is the sibling of finding 11, and it takes away the obvious answer to it.

The GCP backend clears the local copy on write:

```go
secret.EncryptedValue = "" // Don't store value in DB
```

and then the hub writes it straight back, deliberately:

```go
// Re-persist the actual value to SQLite as backup. The backend's Set() stores
// EncryptedValue="" (using a SecretRef), so without this the key material
// would be lost if the secret backend becomes unavailable.
```

With `gcpsm` fully working, the two internal signing keys are still sitting in cleartext in
the local database — refreshed on every boot. The rows carry a valid Secret Manager reference
*and* the raw value.

We purged them. They came back on the next restart, which is exactly what the code says will
happen. There is no reachable state where the hub's internal keys live only in Secret Manager.

The comment is honest and the reasoning is defensible — it protects against a wiped database.
But it means that adopting a managed secret store does not deliver the property most people
adopt it for, and nothing tells the operator that.

## Rotating the keys — finding 22

Since the keys had existed in plaintext since install, we rotated.

The hub logs where its keys come from: `source=shared_secret`. Both signing keys derive
deterministically from `SESSION_SECRET` — we confirmed this by accident, having noticed that
three separate restarts produced byte-identical key material. Rotating the keys therefore
means rotating `SESSION_SECRET`, which invalidates every session and agent token at once.
There is no staged version of this. We took the logout.

Rotation worked. What it does not do is clean up after itself: Secret Manager afterwards held
three enabled versions, the first two being the pre-rotation keys. Nothing disables or
destroys them. Superseded key material stays readable to anything holding
`versions.access` until someone prunes it by hand.

## A config-casing trap — finding 23

`gcp_project_id` and `gcpProjectId` are both correct, for different files. `settings.yaml` is
parsed by the v1 schema and uses snake_case; environment variables land in a different struct
that uses camelCase. There are two lookup tables in the same source file that map the same
token to the two different spellings.

Neither is wrong. But the wrong one for a given path is silently dropped — compounding finding
8, where unknown keys are already ignored without complaint. It is indistinguishable from a
typo. The telemetry block in the same `settings.yaml` genuinely is snake_case, which makes the
file look like it establishes a convention that the environment path does not follow.

## Two calls we got wrong

Worth recording, since both were the same mistake in different clothes.

We flagged the runbook's `SCION_HUB_STORAGE_BUCKET` as wrong on the grounds that it lacked the
`SCION_SERVER_` prefix — reasoning from finding 12, where exactly that had bitten us. Then we
read further: it *is* honoured, but only when the server runs in hosted mode. Our unit passes
`--production`, which is a deprecated alias binding the same variable, so it would have worked
after all. We used the `SCION_SERVER_` form anyway, since it does not depend on a deprecated
flag surviving.

Then we called the runbook's YAML wrong for using `gcp_project_id`. That turned out to be
correct too, for `settings.yaml` — which is how finding 23 got written.

Both errors came from generalising one confirmed bug into a rule. The config layer has enough
genuine inconsistency that pattern-matching against it is not reliable; reading the struct
tags is.

## Where it stands

Secret Manager and GCS are live and audited. Keys are rotated. `hub_id` is pinned.

Outstanding: the cleartext rows come back on every boot and will keep doing so until the
write-back is changed upstream, and the superseded Secret Manager versions still need pruning
by hand.

## Later the same day: a three-day outage, and two hypotheses that were wrong

Users reported that members could not create agents:

```
Failed to dispatch to runtime broker: runtime broker returned error 500:
Failed to start agent: failed to find harness-config "copilot": harness-config "copilot" not found
```

It was reported as a permissions problem, and it is not one. The project's policies were
correct, the authorization check passed, and the failure happens after it, at dispatch. A
denial would have been a 403; this is a 502 wrapping a broker 500.

The harness-config was in the database the whole time — global scope, `status: active`, twelve
files listed. What was missing were the files, in the places the broker actually looks.

### The real cause

The broker resolves a harness-config two ways: hydrate from the Hub's storage backend into a
content-hash cache, or fall back to a local directory (`~/.scion/harness-configs/<name>`). On a
hub-only install both can be empty at once — nothing ever creates that local directory, and
hydration fails whenever the files are not in the storage backend currently configured. The
bundled-resource bootstrap does not catch it, because it skips harness-configs when database
rows exist rather than checking whether the files are reachable.

The only log line naming the real cause is at DEBUG:

```
Env-gather: harness-config hydration failed, falling back to on-disk
error: failed to download file Dockerfile: download failed with status 404
```

Throughout, `/healthz` reported `healthy`.

Filed as issue 24.

### Two wrong hypotheses, in order

**First: "the storage switch this morning caused it."** It was the most recent change and the
timing looked right. The logs disproved it immediately — the first failure predated it by three
days. The operator said as much before we finished checking, and was right. Reaching for the
most recent change is the obvious instinct and it was wrong here; one timestamp query settled
it.

**Second: "issue 20 caused it — the `hub_id` flip moved the storage namespace."** This was
wrong in a more interesting way. It was a coherent story, the evidence cited was real, and it
belonged to a different subsystem: the hub's own resource store is hub-scoped, but the broker
never consults it by that path. What disproved it was reading where the error is actually
raised — `pkg/agent/provision.go`, whose comment says plainly "load harness-config **from
disk**".

The correction that mattered came from a question rather than a log: *if a missing global
directory were the cause, why did my project work and theirs not?* A missing shared directory
fails for everyone equally. That question is what forced the two-path explanation, and the
content-hash cache is what explains the asymmetry — once any start hydrates a config
successfully, later starts of that same config hit the cache regardless of who asks. The
variable was *when*, not *who*.

### And a third thing wearing the same costume

While testing as a non-admin, the Create Project page threw:

> You don't have permission to perform this action on this resource.

before anything was typed. The page issues `GET /api/v1/github-app` on load — admin-only — and
renders the 403 as an unscoped global error toast. No `POST /api/v1/projects` appears in the
logs at all; nothing was submitted. Clicking through it creates the project normally.

That is almost certainly what stopped the team in the first place, and it is why this read as a
permissions problem from the very beginning: two unrelated failures, one of them a false alarm,
arriving together. Filed as issue 25.

### Verified end to end

With both resolution paths repaired, a fresh project and agent were created **as a member, not
an admin**, and the container reached `running`. Four agents running across four projects.

The new project was created with only two auto-generated policies — `agent: [create, stop_all]`
and `gcp_service_account: [assign]`, and no read policies. Issue 18 reproduces exactly as
described on the current build.

**Findings recorded: 25.**
