# 2026-08-25 — Rebuilding every image behind a corporate proxy, and a wrong turn on the way

The goal was mundane: get a current `sciontool` into the agent images so the `--scope` flag
works without patching binaries into running containers by hand. Doing it properly meant
rebuilding the images from source. That turned out to be impossible as shipped, produced a
concrete patch we are running now, and surfaced two new findings along the way.

## No image builds at all behind a blocked registry

The first attempt died on the root image:

```
npm error code ECONNRESET
npm error network request to https://registry.npmjs.org/chrome-devtools-mcp failed
```

`core-base` is the base of the entire DAG, so this is not a partial failure — **zero of the
eleven images build**. What makes it a finding rather than a fact of life is that there is no
knob. Six of the eleven images fetch from npm or pip, and every one of them addresses the
public registry directly.

Worth noting what *did* get through in the same build: `deb.debian.org` pulled 72 packages,
`dl.k8s.io`, `go.dev` and `raw.githubusercontent.com` all fine. Only the language package
managers are affected.

Details and the patch are in [issue 9](../FINDINGS.md), which we rewrote today — it had been
filed as a minor `make web` annoyance and it is considerably more than that.

## A wrong turn worth recording

With the mirror configured, six packages still 404'd:

```
@anthropic-ai/claude-code · @openai/codex · @google/gemini-cli · opencode-ai · @playwright/cli
```

Four of the five are AI coding CLIs. We concluded the corporate JFrog Curation policy was
deliberately blocking AI tooling pending approval — which is an entirely plausible thing for
an enterprise to do, fit the evidence, and was **wrong**.

The control that broke it was fetching a package nothing had touched:

```
tiny-invariant   anon=404   auth=200   anon-after=200
```

The mirror returns 404 for anything not already in its cache, and only an *authenticated*
request causes it to fetch from upstream. Every one of those packages was simply cold. Once
authenticated, all six installed — including `@anthropic-ai/claude-code@2.1.235`.

The lesson generalises past our environment: on a caching mirror, "package not found" and
"you are not authenticated" are the same error message. We had assumed a policy decision from
a 404 for about half an hour. If the upstream docs ever cover the mirror case, that failure
mode deserves a sentence.

## The credential cannot be a build-arg

The obvious way to pass mirror credentials is a build-arg. That would be a mistake: build-args
are recoverable from `docker history`, so any published image leaks the token. We used a
BuildKit secret instead —

```dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc,required=false npm install -g chrome-devtools-mcp
```

— gated on an optional `NPM_CONFIG_FILE` in the local-docker and local-podman builders, with
`required=false` so unauthenticated builds behave exactly as before. Verified afterwards that
`docker history | grep -c authToken` returns `0` for every image.

Eight images built. `hermes` then failed on the pip half of the same problem, which we have
not fixed.

## Two more findings

`hermes` failing surfaced [issue 27](../FINDINGS.md): `--target` accepts only groups, not
individual images, and the run aborts on first failure. `hermes` sorts before `opencode`, so
one blocked pip install took down two images that had nothing to do with it. Getting the one
image we needed meant hand-writing a `docker build` and reproducing the `BASE_IMAGE` wiring
the orchestrator normally computes.

Then we wanted to hide the harnesses this team does not use, which surfaced
[issue 26](../FINDINGS.md). There is no disable operation. `harness-config delete` exists but
does not stick — the bootstrap re-imports any directory still on disk whose row is missing, so
the config returns on the next restart. This is the same shape as the seeded-policy problem in
issue 16, which `65482def` fixed for policies with tombstones; harness configs did not get
that treatment.

The schema already has `status = pending | active | archived` and the list handler filters to
active by default. Nothing an operator can reach ever sets `archived`. We set it directly in
SQLite and moved the unwanted directories aside. It held across a restart, but that is not an
operation an operator should be performing, and we would not bet on it surviving an upgrade
that re-seeds bundled configs.

## Where the hub ended up

Four harnesses visible (claude, copilot, gemini-cli, opencode), four archived. Agents now run
images built from source at `2b8be982` rather than pulled from an upstream personal registry —
which also closes a supply-chain gap we had flagged earlier but had no practical answer for.
`sciontool` in those images supports `--scope`, so the credential-capture path works without
hand-patching containers.

Two caveats we are not going to paper over: only the `copilot` image has been exercised at
runtime, and agents created before the switch keep running their old images until they are
recreated.

# Later the same day — upgrading to `aedf89ed`, and four more findings

We pulled 23 commits and rebuilt. That closed nothing we had open, and opened four new items,
one of which is a direct follow-on to a fix Preston shipped this morning.

## Re-verification: nothing resolved

Every open issue was re-checked against the file it cites, not from memory. All still present
at `aedf89ed`. The upgrade brought the GKE Helm chart work, a `grok-build` harness and a
`DefaultHarnessAuth` setting — none of which touch the areas these issues live in.

Three got sharper rather than closed:

- **Issue 25** — we had the mechanism wrong. `project-create.ts` already treats the 403 as
  non-fatal (`if (!res.ok) return` inside a `try/catch`). The toast comes from `apiFetch`,
  which dispatches `scion:access-denied` on *every* 403 before returning. No caller-side
  handling can suppress it; the fix has to be in the wrapper.
- **Issue 26** — the archive workaround survived an upgrade that *added* a harness. More
  durable than we predicted. Recorded as such.
- **Issue 8** — the re-test was inconclusive and says so. No warning was logged (confirmed),
  but the unknown key was not dropped either, because the rewrite that discards unknown keys
  only fires when `broker_id` is missing.

## Issue 28 — the metrics dashboard, found by reading logs

A member had the UI open and the hub was logging, roughly once a second:

```
WARN  authorization denied  resource_id="/api/v1/metrics/"  reason="not an admin"
```

`/api/v1/metrics/` is `requireAdminHandler`. `metrics-dashboard.ts` has no admin check at all —
we grepped it for `isAdmin`, `role` and `admin` and got nothing. Each view is a separate
request, so one visit produces several 403s, and combined with the `apiFetch` interceptor from
issue 25 that is a stream of permission toasts on a timer.

## Issue 29 — telemetry that has never once worked

Every agent gets `SCION_TELEMETRY_ENABLED=true` and authenticates through Scion's in-container
metadata proxy, which returns 403 because no GCP service account is registered
(`gcp_service_accounts: 0 rows`). The exporter retries forever and logs at `INFO`:

| agent | occurrences of the failure line |
|---|---|
| up ~25h | 3,015 |
| up ~19h | 2,337 |

We assumed this was a GCP IAM problem and it is not — the host's own service account works
fine. Worth stating plainly in the issue, since that is the wrong turn a maintainer would
otherwise repeat.

## Issue 30 — chat renders, then 503s on every send

A member opened Scion Chat and got "Chat not available". Not authorization: the chat routes
answer 401, not 404, so they are registered. `native_chat.enabled` defaults to **true**, but
`SetWebChatStore` is only called inside the message broker's startup block, and
`MessageBroker.Enabled` defaults to **false**. Chat ships on, with a nil store.

One key in `settings.yaml` fixed it, on the in-process adapter, no NATS needed. But
`server.message_broker` is not in `settings-v1.schema.json`, which declares
`server.additionalProperties: false` and lists eleven keys — `native_chat` is missing too. The
one key that turns chat on is one the published schema forbids.

## Issue 31 — the progeny fix, and what is still behind it

Preston diagnosed our sub-agents-get-no-credentials problem this morning and shipped
`4b683622` (#1292, closing #1252): `hasAnyKey` used `agent.OwnerID`, which for a progeny agent
is the *creating agent's* ID, so user-scoped secrets were never found and `NoAuth` was set
preemptively.

**The fix is correct and it is deployed here — the symptom persists.** We upgraded at 19:41;
the agents below were created at 20:32 and 21:38. Three further conditions have to hold:

1. `allow_progeny` is 0 and the capture flow cannot set it. The UI can; `sciontool secret set`
   exposes only `--type/--target/--force/--scope`, and `capture_auth.py` shells out to it.
2. `ListProgenySecrets` matches `CreatedByIn(ancestry)`, but agent-authored secrets store
   `created_by` as `"agent:<uuid>"` while ancestry holds bare UUIDs, and nothing normalises the
   prefix in the secret path. An agent-created secret can never match.
3. With 1 and 2 patched by hand, auth resolves correctly (`selectedType="auth-file"`) and the
   credential is *still* not delivered — `resolveSecrets: resolved secrets count=0 names=[]`,
   `files=0`.

We fixed 1 and 2 directly in the database and watched the behaviour change — `harnessAuth`
went from `none` to `auth-file` — which is what makes us confident they are real rather than
theorised. 3 we could not get past.

There is a distinctive symptom worth documenting: before the fix the failure presents as
`COPILOT_GITHUB_TOKEN` missing. That key belongs to copilot's *other* auth type. When the
progeny lookup finds nothing, resolution falls back to `default_type: api-key` and the operator
is told a token is missing for an auth type they never selected. We spent real time searching
for the wrong thing, and so will anyone else.

Operators can work around all three today by capturing at **project** scope, which resolves
through the ordinary path. The cost is sharing the credential with everyone who can run agents
in that project — precisely what user scope exists to prevent.
