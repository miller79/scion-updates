# 2026-08-31

## Changing a project's git branch requires a database edit

Our Azure DevOps project was created while we were working on a feature branch,
`jisaal1/add-scion-templates`. That branch merged, and we wanted the project on `main`. We
could not find the setting, so we went looking for it in the source.

There is no setting. `scion.dev/default-branch` is written once, by the create-project form
(`project-create.ts:603`), and read by three consumers that all fall back to `main` when it is
absent. `project-settings.ts` has no branch field in any tab.

The API route exists — `PATCH /api/v1/projects/{id}` takes a `labels` object — but it has a
sharp edge we want to flag clearly, because we nearly walked into it. The handler assigns the
map wholesale:

```go
if updates.Labels != nil {
    project.Labels = updates.Labels
}
```

Sending only the label you want to change — which is what PATCH semantics invite — deletes
`scion.dev/clone-url` and `scion.dev/source-url` along with it. The project keeps working until
the next agent creation, then fails with no clone URL, and recovery means knowing the label
scheme well enough to rebuild it from memory.

We avoided that by reading the full label map out of `hub.db`, changing the one key, and
writing it back. Which worked, and is also not something we would ask a normal user to do.

Two smaller notes from the same exercise:

- `PATCH /projects` requires project-owner, so a `member` cannot do this even via the API. On
  our hub the person who uses the project daily is a member.
- The project turned out to be clone-per-agent (no `scion.dev/workspace-mode` label), so there
  was no shared workspace on the host holding the old branch — the label change was the whole
  fix. Had it been a shared workspace, the on-disk clone would still have been checked out at
  the old branch, and nothing in the product would have told us.

Filed as issue 43. The valuable half of the fix is a branch field in project settings; the
important half is making `PATCH` merge labels rather than replace them, since that one is a
data-loss bug independent of branches.

## Wanting an agent without a project, and finding out why it matters

A small ergonomic wish turned into a defect. The wish: create an agent without first creating a
project. Most of what we ask agents to do is self-contained — clone a repo, answer a question,
write throwaway code — and the project adds a naming-and-cleanup step that buys nothing when it
holds no shared secrets, no membership and no canonical checkout.

`projectId` is mandatory (`handlers_agents_core.go:392`), so we went looking for the next best
thing: a project with no git remote, giving each agent an empty workspace to fill itself.

That is not what a non-git project does. Every workspace mode is gated on the remote being set —
both `IsSharedWorkspace()` and `IsWorktreePerAgent()` open with `p.GitRemote != ""` — and so is
the code that writes the label in the first place. Pass `workspaceMode` on a project with no
remote and it is silently dropped. With no mode available, every agent falls through to
`hubManagedProjectPath(project.Slug)`, a path derived from the project slug and nothing else.

So every agent in a non-git project gets **the same directory**, read-write, with no isolation.

We had already been bitten by this without understanding it. A set of agents came up wearing
each other's identities; the harness writes its system prompt into a workspace file, all the
agents had the same workspace, and the last writer won. We assumed we had misconfigured
something. We had not — we were using a shared workspace we never asked for and were never told
about. Moving the work to a git-backed project restored isolation, which at the time looked like
a lucky fix rather than the explanation.

The irony is that `WorkspaceModePerAgent = "per-agent"` already exists and is documented as the
default. It just cannot be selected for a project with nothing to clone.

Filed as issue 44. Honouring `per-agent` for non-git projects is the small fix and removes the
collision; making `projectId` optional — resolving to a per-user scratch project — is the
ergonomic one. Not dropping a field the caller explicitly set is the reason we lost a day.
