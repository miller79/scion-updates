# 2026-09-02

## Re-verifying 44 issues against a fork that is 153 commits ahead

Preston suggested moving from this repo to issues and PRs on a fork he can merge from, which is
the right call. Before filing anything we re-checked every issue against the fork's `fd818e08` —
153 commits on from the `aedf89ed` we had last verified against, and a week newer.

That was worth doing. **Six issues came off the list.**

### The authorization model was rebuilt

Issues 16, 17 and 18 are all resolved, and by a deeper change than we proposed. The seeded roles
are no longer derived from action classes; `hubMemberPermissionIDs()` is now an explicit curated
list that excludes `project.list`, `project.read`, `agent.list` and `agent.read` at system scope.
The comment above it names the exact mechanism we reported:

> Including them would grant cross-project admin-view visibility to every hub member via the
> hasAdminView handler pattern.

There is a `TestGolden_CrossProjectVisibilityRegression` guarding it. `hub-viewer` is now a real
role with its own curated set rather than an alias for member (17), and
`projectMemberPermissionIDs()` grants project `read`/`list`, so membership confers visibility
(18) — which was the trap that made 16's obvious fix hide projects from their own members.

Those three were the top of our "if you only look at" list for five weeks. Good outcome.

### The OIDC guide shipped, without the errors

Issues 4 and 5 were against an unpublished draft sent to us directly. That draft has since been
published as the *External OIDC Login Provider Support* section of
`docs-site/.../single-node/auth.md`, and **neither error made it in**: the draft's two
occurrences of `/api/v1/auth/oidc/callback` are gone, and so is the "requires HTTPS"
prerequisite.

One small thing replaces them. The published guide gives no redirect URI *at all*, and the
reader has to register one in their IdP. The value is still
`BaseURL + "/auth/callback/" + provider` with slug `oidc`. One line would close it. We have
downgraded 4 accordingly rather than leaving a 🔴 standing on a fixed document.

### What has not moved

The mechanical ones are all exactly as reported: the `go1.23.0` pin against `go.mod` 1.26.1, the
`git push origin main`, `--session-secret` in the systemd unit, `EncryptedValue = encodedValue`,
`strings.Replace` on the clone URL, `SCION_STAGED_SECRETS`, `DefaultHubID` off the hostname, the
group-only `--target` list, `scion --version`, and both halves each of 43 and 44 — including
after #1450 touched project settings without adding a branch field.

Issue 30 is half-fixed: `message_broker` and `native_chat` are accepted settings keys now, so the
fix is no longer invisible to `settings.yaml`. Whether chat still renders against a nil store is
a runtime question.

### The limit of this pass

It was static. Roughly a dozen issues — 24, 25, 26, 29, 31, 34, 35, 39, 41 among them — were
originally established by observing a running hub, and cannot be honestly retired or confirmed by
reading source. Issue 31's progeny logic in particular has been rewritten into a new file,
`pkg/hub/authz_relationship.go`, so it needs re-running rather than re-reading.

Our hub is still on `aedf89ed` and deliberately staying there for now, so those stay marked
**NEEDS RETEST** rather than being asserted either way. Filing them as issues without that
retest would put claims in front of a maintainer that we cannot currently stand behind.

A note on filing mechanics for anyone repeating this: GitHub disables Issues by default on forks,
and a fine-grained PAT cannot turn them on without **Administration: write** — the `PATCH` returns
403 even when the account holds admin on the repo. The checkbox has to be ticked in the UI.
