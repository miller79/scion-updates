# 2026-09-07

## The hub is on `8f66d97d`, and four of our fixes came back with it

Preston cleared the upgrade, so the hub moved from `aedf89ed` to `8f66d97d` — 189 commits. The
build was uneventful: web assets in 4.6s, a 222 MB binary, `healthz=200`, and all three
long-running agents survived the restart untouched.

One wrinkle worth recording. The VM's checkout still carried our npm-registry patch as
uncommitted local modifications, which would have collided with the pull. Since that work has
since landed upstream, the patch was redundant — but we stashed it rather than discarding it, so
it is recoverable from `git stash list` if the merged version ever turns out to differ from what
we were running.

**Four of the issues we filed are now fixed by patches we contributed**, merged upstream into
`GoogleCloudPlatform/scion` and present on the VM: the `monitoring.viewer` grant (15), the
`net/url` clone-URL fix (33), the internal npm registry support (9), and the chat terminal link
(36). Their fork issues closed automatically when the PRs did.

The npm work is only half done: pip is still uncovered, so `hermes` remains unbuildable behind a
proxy that blocks PyPI. Worth saying plainly rather than letting "fixed" imply more than it does.

## Retesting the fifteen held items

These were the ones we refused to file in September because they had been established by watching
a running hub, and we were still on the old build. With the upgrade done, we went back to them.

**Two are resolved.**

Issue 34 — a project-scoped `GITHUB_TOKEN` could never authenticate the initial clone — is fixed,
and the fix carries a comment stating the exact reasoning we had reported:

> This must happen before cloneSharedWorkspaceProject so that resolveCloneToken can find it
> during the initial clone.

Issue 6 is obsolete rather than fixed. `scion@localhost` no longer appears anywhere in the
sources, and the development user is now keyed by a well-known UUID with its email read from the
store, so the identity no longer depends on matching an email at all. The bug we described cannot
happen in this shape any more.

**One is half-fixed.** Issue 26: obsolete *bundled* harness-configs are now archived on bootstrap
rather than resurrected, which was the "delete silently reverts" half. There is still no
user-facing way to archive one you simply do not use — the `archived` status exists but nothing in
`harness_config_handlers.go` exposes it. We still hide ours with an out-of-band directory.

**Five are confirmed still present**, and are now filed: 35 (stale project marker), 37
(`inject_when: git_workspace` unreachable in a container), 39 (sibling-container topology
undocumented), 41 (agent output persisted unredacted), and 19 (no zip template import). Issue 7 is
filed in a narrowed form — `hosted/ha/auth-proxy-iap.md` now exists and covers IAP, but the
single-node guide still says TLS setup *"Requires a domain name pointed at the VM's external
IP"*, which is exactly what an internal-only host cannot provide.

**Two we could not reproduce, which is not the same as fixed.** Issue 29's telemetry retry storm
does not occur on our hub because `gcp_project_id` is set — startup now logs one clean line. Issue
30's nil chat store cannot occur because we run with the message broker on. Reproducing either
means deliberately misconfiguring a hub other people are using, so both stay open and unfiled with
that stated explicitly.

**Four remain held**: 24, 25, 28 and 31. Each needs an invasive test — deleting and recreating
projects, spawning progeny agents, or driving the UI as a non-admin — on a shared hub.

## Where things stand

Twelve of the original 44 are now fixed, four of them by our own patches. Twenty-six are filed and
open on the fork; six are held. The fork is the working tracker from here, and every finding that
should be there now is.

One process note for anyone reading this later: the GitHub MCP integration expired mid-session
and reported "token expired". The PAT itself was fine — every REST call returned 200. The
expiry was in the MCP layer's own session, not the credential, and the two are easy to confuse.

## Everything is on the fork now

Nine more issues filed, which empties the backlog this repo was holding:

- **Both proposals** — the role model ([#36](https://github.com/miller79/scion/issues/36)) and
  container support ([#37](https://github.com/miller79/scion/issues/37)) — with their full text in

- **The six that needed live tests we cannot run**: 31, 24, 25, 28, 29 and 30, filed as #38-#43.
- **Finding 45**, the break-glass admin gap, as
  [#35](https://github.com/miller79/scion/issues/35).

The six carry explicit caveats rather than being restated as if freshly observed. Two of them —
29 and 30 — say plainly that we **could not reproduce** the behaviour on `8f66d97d` because our
own configuration no longer meets the precondition, which is not the same as fixed. The others
note where the surrounding code has since been refactored: the authorization layer moved from
`requireAdminHandler` to a declarative `routeMetadataTable`, so 25 and 28 describe a mechanism
that has shifted underneath the symptom.

That felt worth the extra words. Filing six stale observations as current claims would undo the
thing this repo has been careful about all along.

## Retiring this repo

**33 open findings, all filed. 12 fixed, 4 of them by our own merged patches.** Nothing is left
unfiled, so the fork is now a complete tracker and this stops being one.

What does not move is the part an issue tracker cannot hold: eleven dated entries of reasoning,
and specifically the wrong turns. The `strings.Replace` fix that turned out to inject OAuth
tokens into SSH remotes — caught by a reviewer's suggestion, not by us. The half-hour convinced a
set of 404s was deliberate policy. The three-day outage attributed to two wrong causes before the
right one. The issue we filed asking for precisely what the code told us not to do, and had to
rewrite in public.

Those are why the findings read as evidence rather than assertion. They stay here, and this file
stops being maintained.
